4 · Sold mid-24h — card over the dimmed photo, with a real next step.

1 · The photo is never cropped

  • Front layer is object-fit: contain — the whole photo, whatever its ratio. A 4:3 shot loses nothing; a tall shot loses nothing.
  • The leftover space is filled by the same photo, blurred and scaled — so there are no black bars and the frame still feels full-bleed.
  • Top/bottom scrims sit above the photo so the header and the card stay legible on a bright image.

2 · The facts strip is the type's own key_specs

  • Source is already in the DB: property_types.field_config.key_specs / project_types… — 8 candidates per type, ordered by what a buyer of that type cares about (migration 0071).
  • The strip takes the first 4 that actually have a value and renders exactly that many columns. A Plot with 3 → 3 equal columns; nothing is ever blank.
  • The candidate list starts with the fields that type requires, so the strip is effectively always full — and it is the same set the P4 detail screen shows, so the story and the detail never disagree.
  • Zero field names in the component. Changing a type's strip stays an admin/DB change with no deploy (CLAUDE.md rule 7).

3 · Title and the way out to the detail screen

  • Title is the first line of the card: listings.title for a property, projects.name for a project. One line, ellipsis — the story finally says WHAT the listing is, not just its price.
  • The title row carries a chevron and is itself tappable → P4 detail. Same destination as the explicit View property / View project button in the action row, and the same as swipe-up.
  • Share moved out of the story (it lives on the detail screen) so the action row stays three targets: Save · View · Send Inquiry, all ≥44px.

4 · About a VIEW COUNT on the story

  • View / save / lead counts are owner-only today — ownerExtras() in lib/listings/dto.ts strips them for everybody else, and the story viewer's own rule is "no view-count ever exposed" (Doc2 §9.3).
  • So this design shows a "View property" ACTION, not a public views number. If you want the number too, it can only be shown to the poster viewing their own story — say the word and I will add an owner-only line there.

5 · What the /stories endpoint must start returning

  • title, listingId / projectId + href for the detail route.
  • keySpecs: { label, value, icon }[] — built by the same detailBlocks helper the detail DTO uses, so there is one builder, not two.
  • typeLabel (Flat / Plot / Township…), areaLabel, postedAt, negotiable, unitTypes (projects), saved.
  • Nothing here is new data — every one of these already exists on the listing/project row.
