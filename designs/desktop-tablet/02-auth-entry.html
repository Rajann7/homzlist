A · Login — Desktop 1440 (two-pane)

Why two panes, and not a centred card on an empty page

  • The mobile login is a wordmark and a phone field on a white screen. Centred alone on a 1440 monitor that reads as an error page — there is nothing to look at and nothing that says what this product is. The left pane carries the product promise (the same three things the app's own onboarding coach screens say), the right pane carries the form, unchanged.
  • The form itself is untouched. Same +91 prefix and divider, same "98250 12345" placeholder, same disabled Continue until the number is valid, same 11px consent line with Terms and Privacy as accent links, same "or" divider and "Browse as Guest".
  • The rate-limit and number-locked banners still sit at the very top of the form pane, so a returning user sees the reason before the field.
  • Below 1200 the left pane disappears entirely and the card centres — a tablet does not have the width for a split, and a stretched split is exactly the failure this whole set exists to avoid.

D · The gate as a modal — a guest taps a gated action on a browse page (Desktop 1440)

The entry gate on desktop is a modal, not a route

  • On mobile, tapping a gated action (contact a seller, save, post) pushes /login — right for a phone, where a full-screen change is how everything works.
  • On desktop the visitor is mid-browse with a page full of context. Throwing that away for a login screen is the single most common way a portal loses a lead, so the same login mounts as a centred modal over the dimmed page: number → OTP → back to exactly where they were, with the action they tried already carried out.
  • /login stays a real route and keeps working — deep links, bookmarks and the seller host all still land on the full page. The modal is an additional mount of the same flow, not a replacement, so there is one implementation and one set of strings.
  • The guest strip stays: browsing never requires an account, exactly as today.
